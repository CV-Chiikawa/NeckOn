# 자세 모니터링 코드 인계 가이드

## 1. 현재 코드의 성격
현재 프로젝트 코드는 **웹페이지에 적용 가능한 AI 로직을 이미 포함하고 있지만, 실행 형태는 아직 로컬에서 카메라를 직접 열어 테스트하는 Python 프로토타입**입니다.  
즉, **웹 적용이 불가능한 코드**가 아니라, **웹 서비스에 바로 꽂는 형태로 포장되지는 않은 상태**라고 이해하면 됩니다.

현재 테스트 버전은 아래와 같은 데스크톱 실행 구조를 전제로 합니다.

- `cv2.VideoCapture(...)`로 카메라 직접 열기
- `while True:` 루프 안에서 프레임 반복 처리
- `cv2.imshow(...)`로 결과 창 띄우기
- `cv2.waitKey(...)`로 종료/재시작 입력 받기

반면, 실제 웹페이지에서는 가운데 웹캠 영역에 브라우저 카메라 화면을 띄우고, 그 프레임을 백엔드로 보내 AI 결과를 받아 우측 상태 카드와 로그 UI에 반영하는 구조가 됩니다.  
따라서 웹 연동을 위해 필요한 것은 **현재 실행형 코드에서 “카메라 제어/창 출력 부분”과 “AI 추론 로직 부분”을 분리하는 작업**입니다.

---

## 2. 웹페이지 디자인과의 관계
현재 UI/디자인 시안처럼 **웹페이지에 실시간 웹캠 화면 영역을 두는 것 자체는 충분히 구현 가능**합니다.  
문제는 “웹캠 화면을 띄울 수 있느냐”가 아니라, **그 화면의 프레임을 현재 Python 자세 판정 로직과 어떻게 연결하느냐**입니다.

즉 역할은 아래처럼 나뉩니다.

- 프론트엔드: 웹페이지에서 카메라를 열고 화면에 표시
- 백엔드: 전달받은 프레임을 AI 로직에 넣고 결과 반환
- 현재 Python 코드: 자세 판정 로직의 핵심 엔진 역할

따라서 본 프로젝트의 현재 코드는 **웹페이지 적용이 가능한 핵심 AI 로직 구현본**이며, 백엔드/프론트에서 이를 웹 서비스 형태로 감싸는 작업이 추가로 필요합니다.

---

## 3. 백엔드/프론트에서 실제로 필요한 부분
웹 적용 시 필요한 것은 “카메라를 직접 여는 프로그램”이 아니라, **한 장의 프레임을 받아서 자세 판정 결과를 돌려주는 추론 엔진**입니다.

즉, 현재 코드에서 핵심적으로 필요한 것은 아래와 같습니다.

- 초기 모드 추론 로직 (`FRONT`, `SIDE_LEFT`, `SIDE_RIGHT`)
- front posture monitor 로직
- side posture monitor 로직
- baseline 저장, smoothing, 상태 전이 로직
- 최종 판정 결과 생성 (`GOOD`, `CAUTION`, `BAD`, GUIDE 메시지 등)

반대로, 웹 연동 시 제거하거나 바꿔야 하는 부분은 아래와 같습니다.

### 제거/분리 대상
- `cv2.VideoCapture(...)`
- `while True:`
- `cv2.imshow(...)`
- `cv2.waitKey(...)`
- 실행용 print/debug 코드 일부

---

## 4. 웹에 붙이려면 어떤 형태로 바뀌어야 하는가
현재 구조를 웹 연동용으로 바꾸려면, 최종적으로는 이런 형태가 되어야 합니다.

```python
result = posture_engine.process_frame(frame, session_id)
```

여기서 의미는 아래와 같습니다.

- `frame`: 브라우저(웹페이지)에서 보낸 현재 이미지 한 장
- `session_id`: 사용자별 누적 상태를 기억하기 위한 식별값
- `result`: 현재 모드, 자세 상태, 메시지, 점수, 디버그 정보

즉, **웹에서는 카메라를 브라우저가 담당하고**, 백엔드는 그 프레임을 받아 Python 자세 로직에 넣은 뒤 결과만 JSON 등으로 돌려주는 구조가 됩니다.

---

## 5. 왜 session_id가 필요한가
현재 AI 로직은 “한 프레임 보고 끝나는 구조”가 아닙니다. 아래처럼 누적 상태를 사용합니다.

- 초기 뷰 추론 단계
- front/side lock 상태
- baseline 저장 상태
- smoothing history
- 상태 전이 카운트

즉, 사용자 A와 사용자 B의 상태를 섞으면 안 되므로, **사용자별 세션 상태를 따로 보관해야 합니다.**

예시 개념은 아래와 같습니다.

```python
sessions[session_id] = posture_engine_instance
```

이런 식으로 사용자별 엔진 인스턴스를 따로 두면, 웹페이지에서 여러 사용자가 접속해도 각자 독립적으로 자세 판정이 가능합니다.

---

## 6. 현재 파일별 역할
현재 코드 파일은 대략 아래 역할로 이해하면 됩니다.

- `main.py`  
  로컬 테스트용 실행 시작점. 카메라를 직접 열고, 프레임을 읽고, 창에 결과를 띄우는 역할.

- `mode_inference.py` 또는 `mode_inference_v2.py`  
  초기 단계에서 사용자가 front인지 side인지, side라면 left/right 중 어디인지 추론하는 역할.

- `front_monitor.py`  
  정면 자세 기준 baseline 저장, feature 계산, 상태 전이, GOOD/CAUTION/BAD 판정 담당.

- `side_monitor.py`  
  사측면 기준 baseline 저장, feature 계산, 상태 전이, GOOD/CAUTION/BAD 판정 담당.

- `common_utils.py`  
  공통 landmark 처리, 좌표 계산, 오버레이, 보조 함수 담당.

- `config.py`  
  임계값, 시간, smoothing 관련 설정값 관리.

## 7. 백엔드 담당자가 해야 할 핵심 작업
백엔드 담당자는 현재 코드를 그대로 웹에 붙이는 것이 아니라, 아래 방향으로 재구성해야 합니다.

### (1) 실행형 코드를 엔진형 코드로 변경
`main.py` 중심 구조를 유지하지 말고, 별도의 예를 들어 `posture_engine.py` 같은 파일을 만들어 아래 형태로 감싸는 것이 좋습니다.

```python
class PostureEngine:
    def __init__(self):
        ...

    def reset_session(self):
        ...

    def process_frame(self, frame_bgr):
        ...
        return {
            "mode": "FRONT",
            "state": "GOOD",
            "message": "Good posture",
            "score": 0,
            "show_bad_alert": False,
            "debug": {...}
        }
```

즉, 카메라를 직접 열지 않고 **입력된 프레임 한 장을 처리하는 함수**만 남기는 것이 핵심입니다.

### (2) API 형태로 감싸기
예: FastAPI, Flask 등으로 감싸서 브라우저가 프레임을 보내면 결과를 받는 구조로 구현할 수 있습니다.

예시 개념:

```python
POST /process-frame
input: session_id, image frame
output: mode/state/message/score/debug
```

### (3) 프론트와 연결
프론트엔드는 브라우저 카메라를 열고, 프레임을 주기적으로 백엔드에 전송합니다. 백엔드는 그 결과를 JSON으로 반환하고, 프론트는 그 결과를 화면에 표시합니다.

---

## 8. 프론트엔드에서 카메라를 다루는 방식
웹페이지에서는 Python이 카메라를 여는 것이 아니라, **브라우저 JavaScript가 카메라를 엽니다.**

대략적인 흐름은 아래와 같습니다.

1. `getUserMedia()`로 웹캠 영상 받기
2. `<video>` 태그에 보여주기
3. 현재 프레임을 `canvas`에 캡처
4. 일정 주기로 백엔드에 이미지 전송
5. 백엔드 결과를 받아 화면에 반영

즉, 프론트/백엔드 역할 분담은 다음과 같습니다.

- 프론트: 카메라 열기, 프레임 전송, 결과 표시
- 백엔드: 프레임 수신, AI 추론, 상태 결과 반환

## 10. 현재 상태에서의 현실적인 인계 포인트
현재 버전은 **로컬 시연과 테스트가 가능한 AI 프로토타입**이며, 동시에 **웹페이지용 추론 서비스로 확장 가능한 구조의 핵심 로직**을 이미 포함하고 있습니다.

따라서 백엔드 담당자가 추가로 해야 할 일은 아래 두 가지로 요약됩니다.

1. 카메라 직접 제어/창 출력 부분 제거
2. 프레임 입력 → 자세 판정 결과 반환 형태의 엔진/API 구조로 포장

즉, 이 코드는 “웹페이지 구현이 불가능한 코드”가 아니라, **웹페이지와 연결되기 전에 백엔드 래핑이 필요한 코드**입니다.

---

## 11. 인계 시 한 줄 요약
현재 코드는 로컬 카메라 기반 Python 프로토타입이지만, 웹페이지의 실시간 웹캠 UI와 연동 가능한 핵심 AI 로직을 포함하고 있으며, 백엔드에서는 이를 프레임 입력 → 자세 판정 결과 반환 형태의 엔진/API 구조로 감싸서 사용하면 됩니다.
